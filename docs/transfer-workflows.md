# 收款人与订阅整理转账方案

本轮按用户授权完成优先级第二的智能转账与跨场景联动，复用 T14 / T16 的原资金执行、人工确认和预授权链路。上一批账单与订阅增强继续保留，不新增依赖或迁移，不接入真实联系人、外部支付、定时转账或卡片 / 理财写操作。

## 收款人审查

1. 重启服务并刷新，进入“业务办理 → 收款人”。原有本人账户和已登记收款人继续保留，可按姓名、备注、账户尾号搜索。
2. 展开“载入虚构联系人”，重新验证自己的登录密码后点击载入。新增同事张明（尾号 4712）、房东张明（尾号 5938）和朋友林晓（尾号 8620）；重复载入不会重复创建。
3. 三位联系人是本地虚构收款主体，有独立的零余额账户，禁止登录。载入不扣款、不改变本人账户余额、不创建授权，也不公开其他用户。不同用户载入后得到各自独立的联系人账户；不是全局通讯录。
4. 搜索“张明”应看到两项，搜索“房东”或“5938”可进一步区分。点击“向此账户转账”只填入转账表单，不发起资金操作。可重新验证密码编辑备注；备注不改变账户绑定，也不是银行核验的真实姓名或授权。
5. 发起小额模拟转账，确认单展示后端生成的付款账户、已登记收款名称、你设置的备注、模拟银行与尾号、金额和余额预览。关闭 / 拒绝不扣款；批准后应借贷平衡，收款账户真实增加相同模拟金额，付款人无权查看对方资产。
6. 模型模式下问“给张明转 1 元”，助手应先搜索并澄清具体哪位；明确“房东，尾号 5938”后再准备。是否按用户本意选对目标仍需真实模型人工验收，不能把搜索工具返回正确当作模型语义保证。

## 跨场景方案审查

1. 先在“账单洞察”核对支出和依据，再到“订阅管理”决定哪些订阅要取消。疑似项须先经上一轮的显式登记确认，不能直接取消候选。
2. 展开“整理订阅，再安排转账”，明确选择一个付款 / 扣费账户、该账户下 1–5 个有效登记订阅、收款人和固定转账金额。系统不判断用户是否使用订阅，不擅自勾选取消项。
3. 点击“查看方案与资金影响”。核对步骤顺序、收款备注和尾号、本次转账、当前余额和预计余额，以及取消项每登记期预计少支出的合计。后者不是退款或当前到账，不参与转账可用余额计算。
4. 勾选核对，点击“创建方案并前往助手”。系统创建一个新的应用对话并持久化不可变的对象、金额和顺序；此时未扣款，执行策略仍默认为逐笔人工确认。
5. 点击“将此方案交给助手核对”才发起模型请求；离线模式只保存和展示方案，不能自动办理。每笔仍需独立批准；也可在当前对话显式选择范围匹配的预授权，计划本身不授予权限。
6. 核对任务进度和每步回执。拒绝、失败、过期或未知结果时，后续操作停止；刷新恢复原计划与原操作，不自动调用模型或付款。需要更改方案时先核对已经完成的步骤，再明确建立新方案；聊天不能修改原方案约束。

## 接口与约束

- `GET /api/bank/payees`：保留原 ID、名称、账户 ID、币种和尾号，追加 `note`、`kind=self|demo|registered`、`bank_name`，不返回对方余额或所有者。
- `POST /api/bank/payees/demo`：严格对象 `password`，需有效会话、同源、CSRF 和密码再认证。事务中只为当前用户创建一次三位虚构联系人。
- `POST /api/bank/payees/{id}/note`：严格对象 `note`（最长 64 字符）、`password`；同样再认证，不能更换收款账户。备注写原事件表。
- 新只读工具 `find_payees(query)`：NFKC 规范化后按姓名 / 备注 / 尾号做包含匹配。返回 `unique`、`needs_clarification` 或 `not_found`；多项时模型应澄清，不自动取第一项。不是任意自然语言语义检索，不支持手机号查人。
- `POST /api/bank/plans/preview`：`source_id`、`payee_id`、`amount_minor`、`subscription_ids`。服务端重新校验归属、订阅状态、余额和未知结果，返回步骤、资金影响及 `evidence_digest`。不保存或执行。
- `POST /api/bank/plans`：上述字段加 UUID `request_id`、`evidence_digest`、严格布尔 `acknowledged=true`。事务内重算证据后保存到原对话 / 任务 / 事件表。相同请求幂等，改参数重用请求返回 `PLAN_REQUEST_CONFLICT`；预览后余额、备注或相关订阅内容变化需重新预览（`PLAN_EVIDENCE_CHANGED`）。
- 历史接口追加 `workflow_plan`，模型每轮 `bank_state` 带同一后端计划及实际状态。模型没有创建 / 修改方案、载入联系人或编辑备注的工具。
- 原 `Bank.prepare` 事务强制校验选定计划的参数和顺序；直接 API 调用同样不能跳过。只有此前步骤成功，才能新增下一步；换步骤编号重复相同付款被拒绝。原账本、幂等、会话和预授权范围 / 预算检查继续生效。

方案是当前固定的“取消选定订阅，再转固定金额”流程，不是完整通用规划器；不自动编辑任务目标，不跨对话推断重试，不支持无人登录执行。显示的余额只作预览，不冻结资金，执行时仍以当前后端为准。真实模型能否正确澄清、理解取消对象和表达部分完成状态，须独立验收。
