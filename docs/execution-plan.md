# AI-Banking 分步执行计划

编制日期：2026-10-20（Asia/Shanghai）。本文件是开发执行与任务拆分依据，不表示功能已经实现，也不授权一次性执行全部任务、安装全部依赖、提交或推送。

## 1. 当前基础与第一版目标

仓库已完成基础设施初始化及首次推送，现有本地运行程序、运行依赖和集成测试；实际进度以 `PROJECT_STATUS.md` 为准。第一版最终目标面向自建模拟银行，采用一个主 Agent，完成账单分析、订阅管理、智能转账，以及连接三者的跨场景任务。

### 本次追加授权：最小可运行环境

用户于 2026-10-22 明确要求按计划搭建 Agent 运行环境，并提供可对话、查看金额与账户、模拟登录的前端。本次按“认证 → 账户查询 → 只读工具与 Agent → 前端 → 验证”分步完成该链路，覆盖 T03、T04、T12 / T13 只读部分及 T16 交互基础；这项授权扩展了此前仅定稿 T01-A 的范围。

上述最小环境授权不包含 T05–T11、T14；其后用户又明确授权完善银行内核、状态与恢复、授权及业务服务，范围见下一节。两次授权均不将官方规则、模型选型或阶段验收自动标为通过。具体运行范围、模型配置和限制见 [local-development.md](local-development.md)。

### 后续追加授权：终端轨迹与银行后端

用户要求展示 Agent 运行轨迹，并完善银行转账内核、状态与恢复、授权和业务服务。本次按“轨迹 → T05 记账与幂等 → T06 / T07 恢复与状态 → T08 / T09 授权 → T10 / T11 业务服务”依次实现并独立测试。用户明确选择每次开启预授权时自行填写额度、期限和允许收款账户，并重新验证密码，无默认授权。

接口契约见 [banking-services.md](banking-services.md)。本次不启用 T14 Agent 写操作，不扩建 T16 资金界面，不实现 T15 精确上下文恢复或未来记忆 / RAG / 多 Agent；已有数据库增表升级仍需先备份并单独确认。实现和测试完成后停止，队友审查及阶段关卡验收保留。

### 已讨论确认的设计边界

- 第一版直接暴露少量业务工具，不实现工具搜索、MCP 服务或多 Agent 编排。
- 所有资金使用虚构账户和模拟资金，不接入真实银行或支付渠道。
- 提供人工审批与预先授权两种模式，两种模式复用同一个交易执行器。
- 预先授权开启时完成鉴权及明确授权，限定付款账户、币种、有效期和允许的收款账户；Agent 不能自行修改授权。
- 自动转账累计上限按支出口径计算，收款不抵消支出；执行中及结果未知的操作需要保留额度占用。
- 转账通过预先编写的业务代码执行，防止重复扣款、越权、并发超额及单边记账。
- 状态栏由后端生成带时间和版本的快照；模型摘要、聊天记录和状态栏不作为资金或授权事实来源。
- 保留真实消息角色与 chat template；XML 用于标注数据边界，外来内容经过转义，但权限必须在业务服务强制检查。
- 上下文超限前进行预算检查、任务检查点和历史压缩，不能因压缩而丢失授权约束或重做交易。

### 推荐技术基线，待 T00 / T01 固化

两位成员更熟悉 Python，优先采用 Python 后端。建议按需要逐步引入 Pydantic、FastAPI、SQLite 和 pytest；第一版采用单进程模块化结构，Agent 工具在进程内调用业务服务。不得因为本段列出了技术名就一次性安装所有依赖。

具体语言版本、包管理方式、模型供应商与版本、鉴权实现、交互入口和运行环境尚待确认。T01 中核实比赛限制并记录版本与接口决策后，才建立对应配置。

### 第一版不包含

用户长期记忆、RAG、向量数据库、多 Agent、动态工具加载、真实资金接入、理财买卖、卡片管理、定时转账和 AA 收款等扩展功能。必要的会话状态、操作记录与任务检查点属于第一版基础能力，不能因为“长期记忆以后再做”而省略。

## 2. 每次只执行一个任务

1. 用户指定一个任务编号后，只完成该任务及其必要验证；未明确授权开始开发时，计划文档本身不触发实现。
2. 先读取项目指令、状态、相关代码和 Git 差异，确认前置任务已经验收；不能只按编号假定前置工作完成。
3. 给出当前任务的简短实施说明、计划修改的文件、验证方法和不包含的内容；若任务仍跨越多个独立模块，先拆子任务，每次只做一个子任务。
4. 一个任务对应一个明确问题和独立分支，默认一个 PR；不为“顺便完善架构”实现后续任务，不预建未来模块空壳。
5. 使用已有验证工具。需要新增依赖时说明用途和替代方案；不提前创建下一阶段的依赖或脚本。
6. 完成后执行相关验证，检查差异，更新项目状态，并报告剩余问题；依赖该任务的下一步须等验收后再开始。
7. 资金、鉴权、授权和上下文恢复相关任务由另一位成员重点审查。发现检查失败时修复当前任务或说明阻碍，不跳过失败继续开发。
8. 未获明确授权不执行 Git 提交、推送、合并、发布或 GitHub 设置变更。

### 两人协作建议

- 开发者 A 主要负责模拟银行、账本、授权与恢复；开发者 B 主要负责工具、Agent、上下文与交互，双方互相审查。
- 成员账号和最终分工在 T00 确认；共享契约的变更由双方协调，避免并行修改同一接口。
- T10 / T11 可在数据契约稳定后分别推进；T13 / T16 的并行工作须先固定接口。并行不代表允许单个模型自动执行多个任务，也不自动授权启动子 Agent。
- 对账、额度与操作记录始终使用同一后端事实来源，不由不同开发者各维护一套计数器。

### 任务完成记录

任务统一使用“未开始、进行中、待验收、已验收、受阻”状态。在 `PROJECT_STATUS.md` 维护当前任务、实际验证结果和下一任务，不在此计划中堆积日志。T00–T18 的实时状态以该文件为准。

## 3. 第一版任务拆分

### 阶段 A：确认范围与开发契约

#### T00：核实比赛要求与第一版范围

- 前置：无。只整理文档，不实现业务。
- 工作：核实比赛原文与截图来源，更新比赛记录；将三个场景、模拟环境及非目标写入需求，补充可验证的业务用例；确认成员分工、模型与运行限制。
- 待决：累计预算的授权周期与有效期；是否设单笔上限、最低余额；订阅取消是否同样接受范围明确的预先授权。所有金额阈值必须明确配置，不虚构比赛规定。
- 验收：第一版范围、禁止事项和规则依据可查。无法取得完整规则时保留未知项；会影响实现的限制或资金授权参数未定时，不启动相应实现。

#### T01：固化架构、状态与接口契约

- 前置：T00。
- 工作：更新架构文档，确定 Python 版本、环境与包管理方式、最小模块职责、模型适配边界、鉴权与交互方案；定义账户、流水、授权、操作、任务检查点和状态快照的最小契约。
- 核心约束：金额单位与币种明确；同一授权跨会话共享额度；操作编号与业务幂等键由后端管理；人工和自动授权共用执行器；定义合法状态转换及错误结果。
- 验收：双方能按同一接口独立开发，核心成功、失败、未知、过期与撤销路径可解释。提交契约文档，不编写完整模块或未来扩展框架。

##### T01-A：身份认证与会话契约收尾

只定稿凭据来源、密码验证、服务端会话、生命周期、Cookie / CSRF、资源归属与错误行为，并分类记录 G0 待决项。交付及 A01–A20 验收清单见 [authentication.md](authentication.md)。契约完成后停止；G0、T03 实现与安全测试均不得自动标记完成。

#### T02：建立最小运行与检查环境

- 前置：T01。
- 工作：只建立已选语言与包管理配置、格式与静态检查、测试入口及环境准备说明；引入可执行的真实检查后再配置基础 CI。
- 验收：从干净环境能按文档安装开发环境并运行实际存在的检查；配置示例不含凭据，依赖与锁文件变化可审查。
- 限制：不加入 Agent 框架、数据库服务、模型调用或业务工具；不以无断言或硬编码成功的测试表示业务已完成。

### 阶段 B：先完成可独立测试的模拟银行

#### T03：最小身份、会话与访问隔离

- 前置：T02。
- 工作：G0 与认证契约验收后，按 [authentication.md](authentication.md) 的 T03-A、T03-B、T03-C 依次实现本地用户、持久化会话与 API、资源访问隔离；每次只执行一个子任务。
- 验收：未认证请求被拒绝，用户 A 不能访问用户 B 的账户或操作；模型和客户端提交的身份字段不能覆盖服务端身份。
- 限制：不实现资金执行。测试身份注入必须与正常运行入口隔离，不能用任意用户 ID 或明文演示 Token 代替鉴权。

#### T04：账户、流水查询与固定测试数据

- 前置：T03。
- 工作：建立虚构账户、收款人、流水的最小持久化结构和可复现数据；实现权限范围内的查询、筛选和分页，明确时区与日期区间语义。
- 验收：账户及流水结果可追溯；分页不漏记或重复统计，跨用户查询被拒绝；测试重建只作用于隔离的测试数据。
- 限制：不接入真实数据，不实现转账或 LLM；不得删除用户数据来重置演示环境。

#### T05：原子转账与业务幂等

- 前置：T04。
- 工作：实现内部转账执行内核、精确金额与余额检查、借贷记录、持久化幂等键和状态转换；在数据库事务内完成校验与资金变更。
- 验收：成功转账借贷平衡；非法金额或越权调用失败；重复和并发调用同一操作仅产生一次资金效果；争用余额不超扣，异常回滚不留下单边记账。
- 限制：执行器只供内部测试与后续受控授权链路调用，不开放无授权的资金 API，不向模型暴露直接扣款入口。

#### T06：故障恢复、操作查询与脱敏审计

- 前置：T05。
- 工作：实现按操作编号查询、崩溃恢复及关联审计；区分明确失败和结果待核实，避免使用新编号重试同一笔业务。
- 验收：覆盖提交前故障、提交成功后响应丢失、重复请求和重启；恢复后账本与操作结果一致，日志不泄露凭据和不必要的敏感信息。
- 限制：模拟银行无需引入真实支付渠道；不得将本地事务的效果声称为跨外部系统的端到端保证。

#### T07：任务检查点与后端状态快照

- 前置：T06。
- 工作：持久化任务步骤与操作编号的关联，生成带版本、时间、授权信息及业务运行状态的快照；基础事件记录支持恢复和状态回查。
- 验收：重启、换会话或恢复任务不会把已完成步骤重做；结果未知的操作仍待核实；过期快照不能覆盖后端事实。
- 限制：此任务是确定性状态管理，不实现用户长期记忆或用 LLM 总结资金状态。

### 阶段 C：两种授权模式

#### T08：人工审批链路

- 前置：T07。
- 工作：实现交易准备、后端生成的准确确认摘要、操作绑定的确认和取消、有效期与执行时的授权复核。
- 验收：未答复或模糊答复不执行；过期、拒绝、跨用户确认被拒绝；修改金额或收款账户须重新确认；重复确认不重复扣款。
- 限制：不得把客户端或模型传入的 `confirmed=true` 当作授权凭证。先用受控接口与集成测试验证，完整交互界面留给 T16。

#### T09：预先授权与累计预算

- 前置：T08；T00 的相关参数已明确。
- 工作：实现开启模式的鉴权与授权、付款账户和指定收款账户范围、币种、有效期、撤销及累计支出预算；Agent 无权扩大范围。
- 预算：剩余额度 = 授权上限 − 成功支出 − 执行中预占。费用计入支出；收款和退款不自动补额度；仅明确未执行的失败释放预占，未知结果继续占用。
- 验收：覆盖并发额度争用、重复步骤、拆单尝试、策略变更或撤销、过期、跨会话累计和重启；资金执行与预算变化保持一致。
- 限制：额度不足或策略无效时暂停新操作，不因等待超时自动扩权。撤销阻止尚未提交的交易，不把已提交交易当成已回滚。

### 阶段 D：完成另外两个业务场景

#### T10：账单分析服务

- 前置：T04；遵守 T01 数据契约，可与后续银行任务独立排期。
- 工作：实现按时间、商户与已有分类的统计，明确退款、转账和订阅支出的统计口径；金额由代码计算，支持回查依据。
- 验收：固定数据集上的汇总与流水相符，覆盖日期边界、空结果和退款；不以一页流水充当完整账单。
- 限制：不加入 RAG，不把模型生成的金额当统计结果，不把推测分类表达为已确认事实。

#### T11：订阅查询与取消服务

- 前置：T04、T08；如支持自动取消，还需 T09 与对应授权契约。
- 工作：区分已登记订阅和流水推断的候选，明确模拟环境支持的取消操作及生效时间；实现取消的确认、幂等和结果查询。
- 验收：重复取消不会重复产生业务效果；未获授权不取消；不支持取消时如实返回；取消未来扣费不被当作当前现金入账。
- 限制：不擅自替用户恢复订阅或把取消失败伪装成成功，收款请求或提醒等其他能力另开任务。

### 阶段 E：接入工具与单 Agent

#### T12：类型化工具契约与分发

- 前置：T06、T09、T10、T11。
- 工作：将已验收服务封装为少量工具，明确名称、使用条件、参数、错误与输出范围；候选工具包括账户、收款人、流水、汇总、订阅、操作准备及结果查询。
- 安全边界：`prepare_*` 只创建意图，后续由受控链路检查人工或预先授权并调用内部执行器；用户身份由后端注入，参数必须经过运行时校验。
- 验收：绕过模型直接调用也无法越权或跳过授权；工具定义与实现一致，返回结果有长度上限和分页信息，定义顺序固定。
- 限制：仅直接暴露当前需要的工具。未经单独讨论，不实现通用 Shell、任意 SQL、MCP、工具搜索或任意代码执行。

#### T13：只读单 Agent 闭环

- 前置：T12；模型供应商与调用限制已确定。
- 工作：接入一个模型适配器，实现自然语言理解、信息补齐、只读工具调用和有依据的回答；限制单任务步数、超时、重试与调用预算。
- 验收：可查询账户和分析账单；同名联系人、缺失日期等歧义得到澄清；工具失败不会生成虚构结果；对话消息符合模型实际 chat template。
- 限制：本任务先只开放只读工具，不启用资金写操作，不添加多 Agent 或供应商全家桶。

#### T14：Agent 写操作与受控执行

- 前置：T13。
- 工作：启用交易与取消意图工具，串接模式判断、人工等待、预先授权与回执查询；复用已有执行器、任务检查点和幂等关联。
- 验收：人工模式未确认不执行；预先授权范围内可自动执行；超范围或额度不足不执行；模型重复创建同一步意图不会重复支付；完成状态来自后端。
- 注入测试：恶意商户名称、账单备注、外部消息和伪造 XML 标签不得扩大权限；外部文本转义后保持数据身份，模型判断失误也不能绕过执行检查。

### 阶段 F：上下文与交互

#### T15：上下文预算、压缩与恢复

- 前置：T14。
- 工作：实现上下文装配与 token 预算，预留输出和工具结果空间；采用稳定指令与工具前缀、后部状态快照、近期完整消息及历史摘要；超大数据分页或分块处理。
- 恢复规则：持久化检查点先于摘要，授权与资金始终回查后端；摘要保留目标、约束和记录引用，不产生授权或把外来内容升级为指令。
- 验收：在小窗口测试配置下主动触发压缩，覆盖操作提交前后及结果未知时的恢复；不重做交易、不重置额度、不丢失用户最新修改；消息序列合法。
- 限制：不宣称压缩无损或 KV Cache 必然命中，不悄悄截断安全指令；无法安全恢复时暂停新增写操作。

#### T16：最小交互入口与可见状态栏

- 前置：T13、T07；资金交互依赖 T14 / T15 的验收。
- 工作：只实现 T01 选定的一种入口，展示对话、后端交易确认、模式设置、授权详情和运行状态；前端构建先查询 Astryx 模板与准确组件文档，遵循已有样式系统。
- 验收：用户可辨认账户、金额、费用及授权范围；状态栏来自后端，区分待确认、执行中、结果待核实和完成；鉴权信息不进入模型上下文。
- 限制：不同时建设 Web、原生 APP 和多个 IM；界面刷新不反复触发模型，模型文本不能伪造正式交易回执。

### 阶段 G：集成验收与竞赛交付

#### T17：三个场景的跨场景闭环

- 前置：T15、T16。
- 工作：串接“查询订阅支出 → 选择并取消获授权的订阅 → 从当前可用资金向指定账户转账”的模拟任务，覆盖两种授权模式。
- 验收：每步结果与账本可核对，部分成功或中途失败可解释；重启、重复消息和上下文压缩后不会重做已完成步骤；不把未来节省额当已到账现金。
- 限制：不以演示文案替代真实状态变化，不用一个大工具隐藏未经验证的全流程，不自动回滚已生效的独立业务动作。

#### T18：第一版安全、质量与交付验收

- 前置：T17。
- 工作：整合业务、鉴权、授权、并发、故障恢复、提示注入和压缩恢复评测；记录任务成功率、工具错误、耗时、token、缓存使用及成本；从干净环境复现演示。
- 验收：未授权无资金变化；同一业务操作不重复扣款；账本平衡；并发余额与授权预算不超用；未知结果不重发；跨用户隔离有效；敏感信息不进入日志或模型。这些检查必须全部通过。
- 交付：整理实际运行和验证命令、环境示例、已知限制、演示数据及比赛要求的材料。性能和评分目标根据 T00 依据填写，不虚构通过阈值。
- 限制：已知资金或授权缺陷未解决不得标记第一版验收通过；竞赛提交、远程推送及发布需要分别获得授权。

## 4. 第一版之后的目标

以下均为未来研究与实现目标，没有确定具体框架或依赖。先提出独立设计、验证价值和风险，再拆成新任务，不在第一版中预埋完整实现。

| 编号 | 目标 | 开始前必须明确 | 验收方向 |
| --- | --- | --- | --- |
| F01 | 用户长期记忆 | 记忆内容、用户同意、隔离、来源、有效期、纠错、查看和删除机制 | 正确保留有用偏好；撤回和删除生效；记忆不能成为授权、余额或身份依据；防止外部内容污染长期记忆 |
| F02 | RAG 知识检索 | 知识范围与可信来源、文档版本、访问权限、更新方式、引用及无答案策略 | 检索和答案可追溯；权限过滤先于内容暴露；错误或过期资料不伪装为确定规则；用评测比较基础检索与向量检索后再选型 |
| F03 | 多 Agent 协作 | 单 Agent 的实际瓶颈、角色与消息契约、权限、预算、终止及失败处理 | 相比单 Agent 有可测收益；共享同一资金执行器和授权额度；并发或重复委派不重复交易；Agent 之间的消息不自动成为可信授权 |
| F04 | 工具按需加载 | 工具数量与定义 token、选择错误率、供应商原生支持及兼容方案 | 与直接暴露基线比较成功率、费用和时延；稳定前缀和合法工具历史可复用，不把减少定义当成安全控制 |
| F05 | 新业务与后台任务 | 理财、卡片、定时转账、AA 收款、提醒等各自的官方要求与业务边界 | 每个场景独立需求、授权和验收；收款请求不等于到账；定时触发可验证、可撤销、可去重 |
| F06 | 多入口与部署完善 | 实际用户入口、托管环境、数据保留、监控、备份恢复与访问控制 | 单入口稳定后再扩展，部署可复现，故障可定位并恢复；按实际负载决定是否更换存储或拆服务 |
| F07 | 真实金融服务接入 | 官方接口、契约、身份与交易授权、外部幂等及对账要求和适用的安全审查 | 单独立项评估；模拟银行验收不能视为真实资金上线依据，不在原有模拟配置上直接切换生产凭据 |

用户记忆、RAG 和多 Agent 的先后顺序由第一版评测决定，不为追求技术数量而默认全部引入。模型品牌、编排框架、向量库、长期记忆存储等仍保留为未来决策。
