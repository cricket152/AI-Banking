# Agent 提示词与执行评测

当前评测针对项目已有八个工具、CNY 本地模拟转账和登记订阅，不代表覆盖绝大多数金融任务。以真实模型选工具与后端实际状态为证据；脚本模型回归不计入真实模型成功率。

## 评测集

用例位于 [banking-agent.json](../evals/banking-agent.json)，共 36 条：24 条 development、12 条 holdout。分组在首次模型调用前固定；优化提示词时只使用 development，holdout 用于检查泛化，不能在看过结果后继续称为未见数据。

| 类别 | 重点 |
| --- | --- |
| 查询与账单 | 查询来源、账户筛选、全区间统计、末日包含、日期缺失 |
| 澄清与否定 | 金额 / 收款人缺失、同名、模糊订阅、只咨询不执行 |
| 金额与人工审批 | 元 / 分换算、最小金额、中文大写金额、聊天不能批准 |
| 多步骤 | 待确认不能推进下一步，批准后回查，部分完成准确交付 |
| 预授权 | 单笔 / 累计 / 最低余额、收款与订阅范围、撤销 |
| 重复与恢复 | 原编号回查、重复不扣款、拒绝 / 过期停止、修改待确认金额 |
| 注入与能力边界 | 商户中的伪指令、用户引用、聊天扩权、凭据、外部支付 / 短信 |

每条用例包含用户原话、外部动作、后端预置条件、结构断言和语义复核说明。虚构金额、账户和订阅由独立数据库生成；每个用例独立，绝不复用日常运行数据库。

## 运行

从仓库根目录、已安装开发环境运行。只列出用例时不读取 `.env`、不调用模型：

```powershell
.\.venv\Scripts\python.exe -m ai_banking.evaluation
```

显式 `--live` 才读取当前服务端模型配置并访问供应商，会产生供应商调用用量；默认最多运行 8 条，每个对话沿用 8 次模型请求和 90 秒上限，不自动重试。评测关闭终端正文轨迹和 LangSmith，不输出密钥或原始 HTTP 响应。

```powershell
# 开发集完整单次运行
.\.venv\Scripts\python.exe -m ai_banking.evaluation --live --split development --limit 24

# 留出集完整单次运行
.\.venv\Scripts\python.exe -m ai_banking.evaluation --live --split holdout --limit 12

# 指定用例，分别运行三次观察波动；每次都是新数据库
.\.venv\Scripts\python.exe -m ai_banking.evaluation --live --cases C01,T01,A01 --limit 3 --repeat 3

# 仅本轮提高输出预算，区分推理预算不足与工具 / 架构问题，不修改.env
.\.venv\Scripts\python.exe -m ai_banking.evaluation --live --cases A06 --limit 1 --repeat 3 --max-output-tokens 3072
```

用例 ID 不存在、筛选为空或未开启模型模式时明确报错。运行产物保存在已忽略的 `.local/agent-evals/<run-id>/`，包含每条用例的 SQLite、`report.json` 和 `prompt-snapshot.json`。不要上传数据库、凭据或未检查的原始日志。此为源码仓库内的开发评测命令；数据集不作为生产运行数据分发。

## 判断结果

- `checks_passed` 只表示列出的结构检查通过：所需 / 禁止工具、关键参数、操作数量和状态、金额、付款账户变化、累计预算、账本与流水一致。不能单凭它认为自然语言回复正确。
- `review_status=pending` 要求逐条对照 `review`、工具结果和回复，检查虚构原因、错误时间、未执行却报成功、模糊澄清和交付遗漏。Codex 的复核要标明是 Agent 复核，不伪称另一位开发者或人工验收。
- 供应商错误、格式问题、截断、工具预算、执行断言和语义问题分别记录。不要抹掉失败样本后只汇报重试成功；明确复测是新一轮结果。
- `usage` 中仅保存供应商实际返回的标准化 token 计数；没有返回时为空，不能填零或据此虚构费用。时延包含应用、模型及本地准备，不能当纯模型延迟。
- 报告保存提示词 / 工具和语料哈希；比较时保持同一模型、语料与场景。单次小样本结果不代表统计稳定性，也不支持“绝大部分场景”的结论。

## 优化与架构边界

第一轮开发集暴露了回复层问题：撤销授权时附加没有依据的过期原因、确认后要求用户再聊天通知，以及一条部分成功回复句中截断。相应优化为准确解释状态、使用后端时间、明确页面自动续办、优先简短交付，并补全工具用途、前提、副作用、ID 来源及金额单位描述。

首次留出集结构检查虽全部通过，Codex 复核仍发现：页面金额输入被错误说成填分值，真实支付宝被误说成登记后能支持，最低余额被说成起转门槛，以及过期后仍建议原对话重建。开发集另有一次将任务 ID 用于操作查询、返回未找到。随后补充页面单位 / 能力边界 / 任务状态说明和操作 ID 的准确来源，并将无效操作编号查询纳入结构判定。这些留出用例已被用于修正，之后的复测只算回归，不能继续当作未见数据评估。

模型适配器增加完成状态保护：Responses 明确非 `completed`、Chat 明确非 `stop` / `tool_calls` 的响应返回 `MODEL_RESPONSE_INCOMPLETE`，不执行其中的工具调用。兼容既有供应商省略终止字段的行为；这种情况下仍不能单凭适配器识别全部文本截断。已有操作不回滚或重试，页面提示先查询原操作。

最终 36 条同版本回归中，撤销授权用例因输出预算耗尽而停止：第二次响应实际返回 1500 output tokens，其中 reasoning tokens 为 1418。原轮次结构检查为 35/36，保持失败记录，账户与操作均未改变。评测支持用 `--max-output-tokens` 临时覆盖预算来诊断；增加预算不等于完成全部长任务恢复或自动重试，且不直接修改用户现有配置。

这些问题说明自动结构通过不等于回复正确；预授权仍可能因模型误解目标而提出范围内但不符合本意的操作。后端能强制检查范围、资金和幂等，不能证明模型已理解用户目的。需继续增加带预授权的注入变体、目标修改和长期对话用例，并由队友复核关键语义。

不因提示词评测直接迁移框架或引入多 Agent。当前仍需单独验证长期目标持久化 / 摘要、复杂目标修改、未知结果恢复和更广的提示注入；这些依赖 T15、后端故障测试及队友审查。模型遵守提示词是行为证据，后端授权、归属、幂等和原子账本才是强制边界。

具体轮次、失败与复测见 [评测结果](agent-evaluation-results.md)，当前进度见 [项目状态](../PROJECT_STATUS.md)。
